# CompanyAgent · 新云传媒 AI+办公赛道：企业痛点与降本增效验收路线（v1.9）

## 核心定位（给企业代表看）

**不是再做一个聊天机器人，而是把销售做户外媒体提案时的“客户需求 → 假设书 → 证据选点 → 预算组合 → 执行风险 → 审批 → 变更协调”固化为可复用工作流。**

目标客户：上海新云传媒户外媒体业务团队；参赛演示行业只选择 **食品饮料**。企业客户可基于一个品牌活动对 2027 年公交车身、地铁出入口媒体做 100／200／500 万预算情景对照。所有公网数据均为**合成演示**，绝不代表可售、合同、真实曝光或业绩。

## 从企业的“现在痛点”出发

| 实际业务痛点 | 企业损耗的机制 | v1.9 已可演示的缓解措施 | 仍缺的证据／人工门禁 | 可核验的降本增效指标 |
|---|---|---|---|---|
| 新销售接到 Brief 不知道如何做方案 | 高度依赖资深销售，反复确认目标与指标 | **一页 Campaign 假设书**，把客户与品牌、生意目标、活动目标、人群、时间预算、媒体、KPI 及证明方式七要素对齐 | 实际客户确认、历史赢单/失败案例 | 首版提案工时（人工）vs 系统生成+审核工时，按相同复杂度实测 |
| 预算变更导致方案重算、传播不一致 | 每次手动改 Excel/报价单，媒介数量与预算失配 | **同一冻结数据源**分别计算 100/200/500 万情景及相邻档新增/减少单元 | 正式合同价、折扣、制作执行费由销售财务核验 | 每次预算变更到可供评审的方案耗时；重算次数、金额错误率 |
| 商圈覆盖和广告资源分散 | 切多个后台，客户质疑“为什么这条线” | 工具执行轨迹、匹配证据、无覆盖则降级为参考 | 授权可视化导出文件；不得虚构可视化 API | 方案每项媒体有据可查的比例；售前澄清轮次 |
| 档期冲突与夜间施工风险 | 2027 已占用档期、雨天、施工容量导致损失 | 执行清单、上刊照片/下刊照片和结案、天气缓冲及“误一补二”风险提示 | 红豆系统目标窗口实时可售、人力承包方施工能力、合同条款 | 排期返工次数、未提前发现冲突数、上刊按时率 |
| 客户临时换稿/车辆换线 | 多部门相互等待，漏通知导致延误 | 六类变更原因→按责任岗位生成依赖顺序与人工待办 | ERP/合同/制作/审批系统的正式写权限；真实数据owner授权 | 变更开始到部门确认耗时、漏环节数、客户响应时效 |
| 系统接入企业数据与 Agent 工具的安全风险 | 无控制的 API Key、外部 Agent 可能把原始库存与合同外传 | Railway 公网认证网关、仅合成数据、只读工具/审计/审批门禁；企业私有红豆适配器 | 公司 SSO、PDP、VPC、KMS、日志与数据权限评审 | 未授权访问阻断率、敏感原文出网次数（目标0） |

**重要：以上列的是“拟评估的效率指标”，不是项目已经实现的节省工时或百分比。** 只在相同任务的人工组/系统组按统一口径连续测量后，才能计算时间节省，不能用单次演示耗时推断企业 ROI。

## 七要素 Campaign 假设书 / 业务审查合同

正式赛题要求七个方面逐条回到方案：

1. 客户与品牌（食品饮料，脱敏模拟品牌；真实用户信息不得公开）。
2. 生意目标（例如上海便利店新品铺货与试饮转化，明确是**模拟假设**）。
3. Campaign 唯一主目标（认知／到店／促销／拉新），避免目标混乱。
4. 目标人群（人群画像＋活动区域）。
5. 时间与预算（2027 年完整档期＋100/200/500 万档位）。
6. 媒体范围（公交车身、地铁出入口，可组合）。
7. KPI 与验证方式（如客户扫码后台与上下刊监测、结案报告）；目标值如未有客户来源，标注待确认，不填造假的曝光预测。

**v1.9 实现**：客户表单提供明确的 Campaign 业务字段；后端按七项逐条校验并给出缺失项；生成的独立 HTML 同时展示假设书及三个预算档位的媒体增减。没有得到输入时的旧版任务仍可运行，但质量报告给出 `CAMPAIGN_HYPOTHESIS_INCOMPLETE`，不自动捏造客户生意目标。

## 赛题评委标准对照

按企业提供的学生版说明：**业务价值 30／完成度 25／AI 应用质量 20／行业专业度 15／演示表达 10**。不是自评分，不应将功能演示等同于高分。

| 评分维度 | 可以现场真实展示 | 不得宣称已具备 |
|---|---|---|
| 业务价值 | 模拟客户的生意目标与媒体指标一一对应，预算改动有解释 | 真实客户确认、售前降本已量化 |
| 完成度 | Railway 公网登录 → 一页假设书 → 方案 → 100/200/500 切换 → HTML 离线导出 | 未经授权可访问红豆真实实时库存、在线锁位 |
| AI 应用质量 | 受限只读工具编排、质量门禁、可重放、人工审核与 Skill 反馈迭代 | 模型完全自主执行企业操作或跳过审查 |
| 行业专业度 | 价格与库存来源标注；夜间施工/天气、上下刊照片和结案流程、误一补二风险 | 2027 可售已核实，正式刊例与折扣报价 |
| 演示表达 | 一句话痛点、七要素假设书、方案/差异、风险/后续核验，现场改预算 | 使用静态视频代替运行；虚构工作量节省 |

## 未来企业试点路线（与公网演示完全隔离）

**P0 比赛前**：确保合成用户体验真实跑通；输入/输出/预算切换/HTML 可当场演示；公开 UI 无真实客户姓名、客户账单或 API Token。

**P1 授权数据契约**：公司业务与安全负责人审批用途/tenant/有效期；通过私有环境对红豆公交/地铁 GET 做 Schema 及状态字段校验。令牌留在公司 Secret Manager，凭据过期走人工身份流程；可视化没有已授权 API，使用明确授权的离线导出与来源指纹。

**P2 数据可信与报价规则**：统一 `空车数 = 可售` 等字段含义与 2027 时间窗；核对线路等级与价格口径、单位、税费、施工费、库存冲突。目标是**避免产生不可信方案**，而不是不加核验地抓数。

**P3 业务闭环**：将提案审批、客户确认、媒介锁位、制作/施工、监测、结案依次接入企业既有流程；初期只读和“建议工单”，任何写操作、自动通知或自动审批都需另行授权与幂等、回滚验收。

**P4 持续效率评估**：由业务团队记录人工与 AI+人工在相同案例上的耗时、客户修改轮次、重算差错、按时交付率、结案材料完整度，按周期复盘，报告样本数、假设、差异与置信区间。若系统增加人工复核成本，应如实披露并迭代。

## 给现场评委的 90 秒演示

1. 说明：**新销售拿到一个模糊需求，今天要出可交互的媒体提案，客户可能突然把 200 万改为 100 或 500 万。**
2. 输入食品饮料模拟 Brief 与 Campaign 七要素，显示“7/7 已填写（待客户确认）”。
3. 运行 Agent，展示为何选择这些媒体以及缺少覆盖/目标档期时的阻断或人工待办。
4. 用导出的**离线 HTML**现场切换 100/200/500；说明是同一数据重新计算，不是按比例改数字。
5. 触发“客户改稿”变更，演示制作、施工、监测、客户通知影响链。
6. 强调：公网只用虚构库存；红豆真实 GET 接入已备好受限客户端，但**真实联调与生产迁移需企业批准**。

最后请评委回答的不是“模型有多强”，而是：
- 这个业务决策是否有据可查？
- 新人是否能更快产出可审核提案，并减少返工？
- 企业是否可以在不暴露内部库存的情况下试点？
